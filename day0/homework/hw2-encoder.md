## 背景：编码器是怎么"量角度"的

修这个 bug 之前，你得先知道这个角度是从哪来的。**不然你只是在改数字。**

### 电机里有一个"只有一圈的刻度盘"

DJI 的 M3508 / GM6020 这类电机，转子里装了一个**磁编码器**。电调读它，
然后通过 CAN 把角度告诉主控。

关键是：**它报的是一个"圈内角度"，不是"转了多少圈"。**

```text
编码器是 13 位的  →  一圈被切成 2^13 = 8192 格
每一格 = 360 / 8192 ≈ 0.0439 度
电调报给主控的是格数 0 ~ 8191
```

主控这边把它换算成角度，就是我们代码里看到的 `ecd_angle`：

```text
格数 0     →   0°
格数 2048  →   90°
格数 4096  →   180°
格数 6144  →   270°
格数 8191  →   约 359.96°
格数 0     →   又回到 0°      ← 注意这里
```

> 真实仓库 `MasterArm/base/motor/driver/dji_motor_driver.h` 里就写着：
> `int16_t ecd;  // encoder value(0~8191) 编码器值(0~8191)`

### 问题：这个刻度盘只会转圈

假设电机**一直在往前转**，编码器报出来的数是这样走的：

```text
... 8190 → 8191 → 0 → 1 → 2 → ...
                  ↑
              到这里"归零"了
```

**但电机并没有倒回去。** 它一直在往前走。

现在看主控要算的东西：**"这一帧比上一帧，转了多少度？"**

```text
上一帧 ecd = 8191   （约 359.96°）
这一帧 ecd = 0      （0°）

直接相减：0 - 359.96 = -359.96°
但电机实际是往前走了 +0.04°
```

**算出来的数是实际值的几千倍，而且方向都是反的。**

### 所以要做"折算"

工业上的标准做法叫 **unwrap（解缠）**，我们代码里叫归一化：

```text
差值算出来之后，如果它落在 (-180, 180] 之外，就说明"跨圈了"，
用 ±360 把它折回来：

  +356  →  356 - 360 = -4     即"往回走了 4 度"
  -356  →  -356 + 360 = +4    即"往前走了 4 度"
```

**为什么是 ±180 这个界？** 因为相邻两帧之间电机不可能转过半圈——

> 如果真转过了半圈，那这个算法本来就救不了（这叫**采样太慢导致的混叠**）。
> 实际上 CAN 反馈是 1 kHz，一秒采一千次，相邻两帧最多差几度，离 180° 远得很。
> （CAN 是 **Day 3** 的内容，这一份作业用不到它，知道有这回事就行。）

### 回到 HW1 看到的那个失败

```text
用例 3  forward across zero   355 → 359 → 3 → 7
                              359 → 3 这一帧：差值 = 3 - 359 = -356
                              需要走 -356 + 360 = +4 这一支
用例 4  backward across zero  5 → 1 → 357 → 353
                              1 → 357 这一帧：差值 = 357 - 1 = +356
                              需要走 +356 - 360 = -4 这一支
```

**两个方向走的是不同的分支。** 现在代码里只有一支，所以用例 4 过了、用例 3 挂了。

> **顺带说一句**：这个"圈内角度"的坑不只编码器有——IMU 的 yaw 角、
> 舵机的反馈角，只要它是"一圈 360 度"的表示，就都要做这一步折算。
> 以后你在别的模块看到 `normalize180` / `unwrap` / `wrapToPi` 这类函数，
> 现在应该知道它们是干什么的了。

### Task 4 · 想清楚为什么 `+356` 和 `-356` 命运不同

这是整份作业最关键的一步。

现在的实现是：

```cpp
inline float deg_normalize_180(float d) {
  if (d > 180.0f) {
    d -= 360.0f;
  }
  return d;
}
```

把 Task 2 算出来的两个数代进去：

```text
d = +356   →  356 > 180 成立  →  356 - 360 = -4    ✓ 正确（往回走了 4 度）
d = -356   →  -356 > 180 ？   →  不成立，原样返回 -356   ✗ 错了
```

**这就是为什么只有用例 3 挂：两个方向会走进不同的分支，而现在只有一个分支存在。**

**怎么验证：** 你能解释"为什么补一个方向不够"。

## 常见错误

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| 改完 `test_encoder` 还是 3/4，挂的还是同一个 | 只补了一个方向，或者改错了文件 | 回 Task 4，把两个数都代进去算一遍 |
| `test_encoder` 4/4 但 `test_clamp` 挂了 | 改动影响了夹爪逻辑 | 检查你是不是改了 `app/clamp.cpp` 或 `app/arm.h` |
| 编译报 `deg_normalize_180` 找不到 | 没 `#include "base/math.h"` | 补上 include |
| `git diff` 里整个文件都变了 | 换行符问题（CRLF/LF） | 工程里有 `.gitattributes`，`git add` 时会自动归一化；`git diff --ignore-all-space` 看真实改动 |
| 提交时弹编辑器不会用 | 没加 `-m` | `git commit -m "消息"`，或按提示先配置编辑器 |
